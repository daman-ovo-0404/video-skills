# 模型与节点检查

这里记录稳定的判断方法。支持模式、额度、价格和参数随账号与版本变化，执行前以当前清单、schema 和实际命令帮助为准；不把历史快照当可执行配置。

## 模式选择表

| 当前镜头需要 | 优先检查的模式 | 要验证的条件 |
|---|---|---|
| 已有首帧，只增加运动 | 单图图生视频 | 输入是否作为首帧，运动是否破坏结构，是否意外切镜 |
| 起点与终点都需确定 | 首尾帧 | 模式实际是否收两图；两帧主体、空间、光线能否合理过渡 |
| 角色、服装、产品、场景共同约束 | 多素材参考 | 每类媒体数量与合计限制；输入职责是否清楚 |
| 一段视频按多张分镜依次呈现 | 分镜参考/多素材参考 | 整张分镜图负责顺序，产品多视图负责外观；两者与单幅首帧区分；模式是否支持此输入需核实 |
| 跟随指定表演或动作 | 动作/视频参考 | 是否同时需要人物图与动作视频；朝向、裁剪和原声如何处理 |
| 修改已有视频的外观或内容 | 视频编辑 | 是编辑、续写还是重生成；哪些原有动作应保留 |
| 按已确认音频驱动说话 | 音频驱动 | 必需图片与音频、时长、实际说话对象；多角色分别口型需实测 |
| 将实拍或已生成片段按入出点拼接 | 时间线/视频剪辑 | 每段入点出点、排序、音量与总时长；仅连线未必表达这些参数 |

生成声音的开关不等于接受参考音频，也不等于指定台词、音色或精确口型。一个视频中包含多个镜头、生成多个候选、分镜表有多行，是三件事。

## 配置前的最小核对

1. 查询当前账号可用模型，再读取候选模型对应模式的完整配置。搜索清单的展示名、schema 查询 key 和创建时接受的值可能不同，按当前 CLI 说明使用。
2. 同时核对媒体数量与必需组合。顶层规则可能要求“图＋视频”或“图＋音频”，数量上限合规不代表组合完整。
3. 核对该模式自己的声音、品质、分辨率、时长和多镜头开关。不要把另一模式的参数原样复制过来。
4. 用实际入边对照输入列表与提示词，确认没有失效、重复或旧版引用。

schema 主要确认媒体组合与参数，未必列出“理解九宫格顺序”这样的语义能力。能接多图不保证能按分镜执行；没列专门的分镜字段也不等于不支持。结合当前官方模式说明判断，已授权生成时用相关小样验证；只准备任务可以先完成参考职责与镜头表，保留效果待验证，不虚构配置字段。

过去的在线核验曾遇到：名为 `frames2video` 的模式实际只接受一张图；同一模型首尾帧模式缺少单图模式的声音开关；旧 key 能查到 schema、当前模型搜索却未列出；语音模型重名且查询失败。这些是需要实时检查的原因，不代表问题永久存在。

## 节点操作容易漏掉的事

- CLI 引用格式与入边是两层条件。`{{Node "唯一节点名"}}` 或 `{{Node nodeKey}}` 要对应真实入边；自然语言“参考图一”不能替代连线。
- 新增 `--left` 通常保留已有边。替换素材后查询已有边，用当前帮助中的移除方法清理失效引用，再回读。
- 文本节点的生成提示与已有正文分开；脚本表的静帧、运动、对白和音效字段也分开。改了提示不代表已有结果更新。
- `script storyboard` 可直接执行图片生成，不能因为未写 `--run` 就把它算作纯准备操作。调用前核对当前命令的副作用与用户任务。
- 工作区容器与具体画布是不同对象。修改前确认目标画布，写后回读关键节点、入边和设置；节点同名时使用可唯一定位的标识。
- 批量脚本表生成多版同名分镜时，将行号、脚本版本、候选节点 ID 与实际采纳的媒体对应起来。若还未挑选，保留候选状态；同名镜号不能证明具体素材来源或已进入剪辑。依据：[C13](case-evidence.md)。
- 快捷入口、三视图、九宫格可帮助找构图，生成出来的不可见结构需要真实资料核对。也应检查快捷入口会原地修改还是另建节点。
- 拼图可以是多镜头视频的分镜参考，无须一律拆散。先明确当前模式如何消费它：首帧模式通常选单幅，多素材模式可在支持的前提下引用整张分镜表。九宫格数量不保证最终视频恰有九个镜头。
- 同一画布中出现音频素材，不能证明该视频接收了它。核对具体入边与输入列表，区分音频参考、节点自带声音和后期混音。
- 首尾帧转场要核对实际输入槽的顺序、生成视频的起止画面，以及中段的道具接触和空间变化。名为“首帧/尾帧”的两个节点即使都已连接，也不能代替这三项检查。依据：[C15](case-evidence.md)。

CLI 操作细节来自 2026-09-18 的官方文档与在线配置核查；调用时再以当前帮助为准。带案例编号的条目来自公开画布观察。

## 把失败放回对应环节

| 实际表现 | 先查哪里 | 有针对性的下一步 |
|---|---|---|
| 角色或产品变成旧版 | 入边、输入列表与首帧 | 清理旧引用，明确素材职责，再看结构是否改善 |
| 接了图但提交失败 | 当前模式与媒体组合 | 调整为支持的输入，或换支持该任务的模式 |
| 动作缺失或瞬移 | 动作次序、接触过程、目标时长 | 删除无关动作、明确必要接触或拆段 |
| 有声音但说错人/词 | 声音模式、说话者与音频 | 分清旁白和画内说话，必要时独立处理台词与表演 |
| 任务有 ID 但没有可用结果 | 任务终态与实际资源 | 按当前接口等待同一次生成；CLI 已在等待时继续原进程，异步接口才查同一任务，不虚构轮询命令或重复提交 |
| 文字写 16:9，实际尺寸不同 | 节点设置与媒体文件 | 以实际输出检查；文字参数不替代平台参数 |

完成标准随任务：准备节点看回读；生成看终态与媒体；镜头质量看播放；导出交付再看文件与完整播放。保留有用版本，改名和高清处理也不能替代这些检查。


## 复用节点时的字段与资源核对

2026-09-28 五项目研究新增以下检查，具体案例见[视频依据](video-case-evidence.md)：

- 同时保留提示时间、`params.settings.duration`、顶层 `params.duration` 与资源实测时长。P1付款节点分别可读到14、5与14.08秒；字段不同需追查来源，不能取任一层就判定生成失败。
- 当前 `params`、`isStale`、保存媒体与历史tracking分别读取。`isStale=true`提示可能未按当前参数生成；`false`也不能证明每个冗余字段属于同次提交。当前图有环时，更不能将边直接当制作时间顺序。
- 逐项核对提示引用、当前节点存在、真实入边及实际输入资源。P2同一音频仍留在输入URL记录中，但其节点和边已缺失；不能从这份快照断言历史任务未接入音频。复用时需重新建立当前有效输入。
- 重拍记录中的源版本、区间与输出时长分开保存。区间为空时不补猜秒数；局部补句后输出可能变长，需重算剪辑替换位置。
- `resourceMeta.mimeType=text/plain`可能与实际媒体不符；时长/格式缺失或矛盾时，用已获准下载的文件做媒体探测。
